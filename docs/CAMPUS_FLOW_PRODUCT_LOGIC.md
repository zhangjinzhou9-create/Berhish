# Campus Flow 完善后产品逻辑（供答辩与外部 AI 审计）

更新日期：2026-07-22

## 1. 产品一句话定义

Campus Flow 是一个面向留学生的个人校园仪表板：根据个人所在地提供当日环境信息，集中维护学生资料，并生成可提交或打印的简历。

它不是论坛、导航站或多人管理后台。它解决的是一个连续的个人任务：

> 登录 → 查看今日信息 → 维护个人资料与常用地点 → 导出简历。

网站没有新增独立“项目说明页”。产品定位直接体现在首页标题、导航、账户面板和资料操作中，避免为了说明产品再制造一条用户任务。

## 2. 用户与权限模型

面向真实用户的界面只有两种状态。

### 访客

- 可以查看 Today 页面、搜索国家和城市、读取天气/国家/生活建议。
- 可以查看公开的简历预览并导出或打印。
- 不可以修改数据库中的资料或把地点保存为个人默认值。
- 匿名调用 `GET /api/profile` 时不会返回 `studentId` 和 `phone`。

### 已登录所有者

- 拥有访客的全部读取能力。
- 可以编辑并保存个人资料。
- 可以把 Today 中搜索的国家和城市保存为个人默认地点。
- 可以看到自己的学号和电话；公开简历预览仍不显示这两个字段。
- 可以根据 OAuth 登录来源使用一个对应的连接服务。

“所有者”当前代表这个单人作品站的维护者，不代表已经实现了多租户用户系统。

## 3. Google、GitHub 与 JWT 的真实区别

### Google OAuth

- 用 Google 身份完成登录。
- 登录后允许编辑同一份 Campus Flow 资料。
- 授权 Google Calendar 后，账户面板可以读取主要日历中最近的日程。
- 用户价值：把近期课程/安排带进个人校园仪表板。

### GitHub OAuth

- 用 GitHub 身份完成登录。
- 登录后允许编辑同一份 Campus Flow 资料。
- 账户面板可以读取 GitHub 个人资料和最近更新的公开仓库。
- 用户价值：让学生快速检查可用于简历或答辩展示的开发作品。

GitHub 能力原本已经存在于后端，但只显示在隐藏的技术测试区，因此用户感觉“没有实现”。现在它被放入可见的账户流程，并以人类可读的资料/仓库列表显示，而不是显示原始 JSON。

### 本地 JWT 账号与 STUDENT / TEACHER / ADMIN

- 这是课程要求和 API 权限验证证据，不是当前产品的业务角色模型。
- STUDENT、TEACHER、ADMIN 用来证明注册、密码哈希、JWT 签发和受保护端点的角色限制。
- 这些角色没有不同的资料库、审批流程、班级管理或管理后台，因此不应在普通用户界面中冒充真实管理功能。
- 技术测试区继续保留在代码/API 中以便老师验收，但从产品导航中隐藏。
- 匿名注册只能创建 STUDENT，不能自行提权为 TEACHER 或 ADMIN。

## 4. 为什么当前不做“三类账号的数据区分”

当前数据库模型保存的是一份全局个人资料，而不是“每个登录账号拥有一份 profile”。如果在界面上声称 STUDENT、TEACHER、ADMIN 各自管理不同数据，会造成虚假产品逻辑和实际越权风险。

这次采用单人作品站模型，是因为它与现有数据结构、两天内的提交期限和真实功能一致。它不是为了数据库作业临时制造三套无意义页面。

如果未来要变成真实多人系统，必须先完成以下结构性工作，而不是只增加角色按钮：

1. 给 `profiles` 增加不可伪造的 owner/user 外键。
2. OAuth 身份和本地账号映射到统一用户表。
3. 所有资料查询和更新都按当前用户过滤。
4. 明确定义教师或管理员的业务对象，例如课程、学生名单、审核任务。
5. 增加对象级授权测试，证明 A 用户无法读取或修改 B 用户数据。

这些工作不属于当前提交版的最小修正范围。

## 5. 页面信息架构

### Today

存在原因：学生每天打开网站最先需要的是“我所在地点今天怎么样”。

解决的问题：把国家、城市、天气、国家概况和生活建议组合成一个可立即使用的日常入口。

主要操作：

- Search：临时查询任意国家/城市，不要求登录。
- Save to Profile：登录后把本次地点写入个人资料，之后作为默认地点使用。

时间显示使用天气数据源返回的城市时区和当地时间，不把服务器时间或浏览器时间误当成目标城市时间。

### My Profile

存在原因：把分散的学生信息整理成可维护、可展示、可提交的个人资料。

解决的问题：所有者在同一处编辑资料，访客看到的是安全的公开简历预览。

主要操作：

- Edit：仅所有者可用。
- Save：只在编辑状态可用，保存失败时保留编辑状态并显示真实错误。
- Cancel：丢弃本次未保存修改，恢复服务器最近返回的数据。
- Export PDF / Print Resume：打印公开简历预览。

### Account

存在原因：集中处理身份确认和第三方服务连接，不把 OAuth 技术术语散落在用户页面。

未登录时说明两个入口的具体差异；登录后显示当前身份、provider、对应服务按钮和退出入口。

## 6. 数据与持久化流程

### 读取

- `GET /api/home`：组合国家、城市、天气和生活建议；外部接口失败时可使用本地 fallback。
- `GET /api/profile`：从 MySQL 读取资料；匿名响应会删除学号和电话，所有者响应包含完整字段。
- 前端不会显示“Database status”或 API 路径等生产诊断信息。
- 读取层会兼容还原旧 MySQL 连接曾造成的可识别姓名乱码，但不会在用户未保存时擅自改写数据库原始行。

### 写入

- `POST /api/profile`：只接受有效 OAuth 会话或有效 JWT。
- `ProfileService` 把资料写入 MySQL，并返回 `saved`、`profile` 等明确结果。
- Today 的保存地点与 My Profile 的保存资料共用同一持久化入口，避免出现两套互相冲突的数据。

### Docker

- 应用容器是可替换的运行单元，不保存长期资料。
- MySQL 数据存放在命名卷 `campus_flow_mysql_data`。
- 重建或替换应用容器不会删除该卷，所以资料继续存在。

### Azure

- 云端运行应用容器，长期资料必须连接 Azure MySQL 等外部持久化数据库。
- 容器本地文件系统不是可靠的数据存储；容器重启、扩容或部署新镜像时可能被替换。
- 当前模型仍是单份全局资料，即使云数据库持久化成功，也不等于实现了按用户隔离。

## 7. 安全边界

已经明确并验证的边界：

- 匿名用户不能写资料。
- 匿名资料响应不包含学号和电话。
- OAuth 或有效 JWT 才能读取完整私密字段并写资料。
- 匿名注册不能指定 ADMIN/TEACHER 实现提权。
- 本地密码使用 BCrypt 哈希，不以明文保存。
- JWT 密钥由环境变量提供，旧源码密钥不能伪造管理员令牌。
- 外部 API 数据在账户面板中通过 `textContent` 创建节点，不直接拼接为可执行 HTML。

仍需诚实说明的边界：

- 这是单所有者作品站，不是多用户 SaaS。
- email 仍作为公开简历联系方式；如不希望公开，应进一步从匿名响应和预览中删除。
- OAuth provider 控制“能调用哪个第三方 API”，不是业务角色或数据库数据分区。
- Google OAuth 的测试/发布状态、redirect URI 和 Calendar scope 必须在 Google Cloud Console 中与部署域名一致。
- GitHub OAuth callback URL 必须与当前部署域名完全一致。

## 8. 关键状态流

```text
访客打开网站
  ├─ Today 搜索地点 ──> 仅临时查看
  ├─ 点击保存地点 ──> 打开 Account 登录
  └─ My Profile ──> 公开预览（隐藏学号/电话）

OAuth 登录成功
  ├─ 重新读取完整 profile
  ├─ 可编辑/保存资料与地点
  └─ Google -> Calendar 日程
     GitHub -> 个人资料 + 最近仓库
```

## 9. 本次最小修改的理由

- 删除 Quick Access 和通用书签：它们让网站像开发者入口/导航站，与主任务无关。
- 不新增项目说明页：定位直接写入现有页面，减少实现和认知成本。
- 不创建虚假的教师/管理员界面：现有业务没有支撑这些角色的真实任务。
- 把已完成的 GitHub/Calendar API 放到 Account：复用既有后端，不新增独立模块。
- 增加公开/私密字段过滤：这是数据边界修复，不只是视觉隐藏。
- 增加取消编辑、正确的禁用状态和登录引导：让保存行为可预测。

## 10. 外部 AI 审计建议问题

请审计者重点回答：

1. 匿名访问是否仍可通过其他端点获得 `studentId` 或 `phone`？
2. 任意有效 STUDENT JWT 是否都被视为“所有者”，这在单人部署中是否可接受？
3. `POST /api/profile` 是否存在未过滤字段、并发覆盖或对象级授权问题？
4. OAuth session、JWT 和 CSRF 策略是否与当前 Spring Security 配置一致？
5. Azure 环境变量是否把数据库、JWT、Google、GitHub 密钥与开发默认值彻底分离？
6. 云数据库连接失败时，服务是否会误报保存成功或退回不可持久化的本地数据？
7. Google Calendar scope 是否遵循最小权限，GitHub 是否只申请读取公开资料所需权限？
8. 如果未来改成多用户系统，哪些表和接口必须先增加 owner 约束？

## 11. 答辩时可以直接使用的表述

“Campus Flow 不是一个虚构的三角色管理系统。提交版把它定义为单所有者的留学生校园仪表板：访客可以查看今日环境和公开简历；登录所有者可以维护资料和默认地点。Google 与 GitHub 登录除了确认身份，还分别连接 Calendar 日程和开发作品。课程要求的 JWT 角色权限作为后端安全证据保留，但不会冒充没有真实业务流程的用户功能。数据库目前持久化一份个人资料；我明确没有把它包装成已经完成的多用户数据隔离。”
